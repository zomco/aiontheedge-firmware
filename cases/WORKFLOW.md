# 迭代工作流

> **AI 设计 → 机器验证 → 人工确认。**
>
> 这个分工不是组织架构，是**能力边界**：十三个版本的统计事实是，
> 可手算复核的东西 AI 很少出错；需要空间想象的东西 AI 几乎必错，
> 而且**发现不了自己错**（DESIGN_NOTES §7.9）。
> 所以凡是能翻译成判据的，一律交给机器；剩下的才交给人和打印机。

```
        ┌──────────────┐
        │  ① AI 改设计  │  改参数 / 改结构 / 同步补自检规则
        └──────┬───────┘
               ↓
        ┌──────────────┐   FAIL → 回 ①（几分钟一轮，可以随便试）
        │  ② 机器验证   │  python build.py check   110+ 条规则，约 3~4 分钟
        └──────┬───────┘
               ↓ PASS
        ┌──────────────┐   看渲染 / 看切片预览 / 看模拟画面
        │  ③ 人工审图   │  发现问题 → 把它写成新的自检规则，再回 ①
        └──────┬───────┘
               ↓ OK
        ┌──────────────┐   先打小件试配，再打整机
        │  ④ 试打验证   │  发现问题 → **先补自检规则**，再回 ①
        └──────────────┘
```

**唯一的硬规矩：④ 发现的每一个问题，都要先变成 ② 里的一条规则，再去修。**
否则同一个错误会在下一版重现 —— 这在本项目已经发生过不止一次。

## ① AI 改设计

### 常见动作

| 想做什么 | 改哪里 |
|---|---|
| 微调一个尺寸 | `wmcase/params.py`（**唯一允许出现尺寸数字的地方**） |
| 改一个零件的形状 | `wmcase/parts/*.py` |
| 改尺寸链 / 基准面 | `wmcase/layout.py` |
| 改装配顺序 | `wmcase/assembly.py`（改完 `ASSEMBLY.md` 自动跟着变） |
| 加一条检查 | `wmcase/checks/*.py` |
| 换开发板 | `params.BOARDS` 加一条 `BoardSpec`，见 DESIGN.md §11 |

### 快速迭代技巧

```bash
python build.py check --only OPT,LED      # 只关心光学时，20 秒一轮
python build.py check --skip SEQ,DFAM     # 跳掉最慢的两类
python build.py params                    # 打印当前全部参数和派生量
python build.py sim                       # 只出模拟画面
```

### 改之前先问自己

1. 我依赖的数字是 `[实测]` 还是 `[估算]`？（`params.py` 里有标）
2. 这个改动会不会动到**尺寸链**？（会的话去 `layout.py`，别在建模函数里现算）
3. 改完之后，**哪条现有规则会先发现我改错了**？如果一条都没有，
   说明这块地方缺检查 —— **先补检查，再改设计**。

## ② 机器验证

```bash
python build.py check
```

### 输出

* 终端：按分类分组的 PASS / FAIL / WARN 表（跑的时候有进度，整套要几分钟）
* `out/report.md`：带"这条规则为什么存在"的完整报告，**进 git**
* `out/report.json`：结构化，方便脚本做版本间 diff

### CI 也会跑

`.github/workflows/case-check.yaml`：只要 `cases/` 有变动就自动跑一遍
`build.py check`，报告和模拟画面作为 artifact 传上来（**失败时也传**，
那时候它们才最有用）。CI 不导出模型 —— 导出物是本地生成的，不进 git。

### 三种严重度

| 级别 | 含义 | 会不会挡住导出 |
|---|---|---|
| `ERROR` | 必须修 | **会**（除非 `--force`，而 `--force` 出来的文件不许打印） |
| `WARN` | 可以带着上机，但要知道自己在冒什么险 | 不会 |
| `INFO` | 只报数值，不判定 | 不会 |

### 十个分类

| 分类 | 管什么 |
|---|---|
| `TOPO` | 单一连通实体、拓扑有效、体积量级 |
| `FIT` | 装得进去吗（件间干涉、包络、模组落位、泡棉厚度） |
| `CONS` | 装上会不会掉（**全部是反向测试**） |
| `SEQ` | 按这个顺序装得起来吗（沿路径碰撞 + 全程净空） |
| `OPT` | 相机看得见吗（逐点光线追踪、有效口径、字符像素、景深、渐晕） |
| `LED` | 会不会有高光/阴影 |
| `DIM` | 尺寸链与净空 |
| `DFAM` | 打得出来吗（悬垂面积、壁厚采样） |
| `POKA` | 装反了会怎样（**全部是反向判据：必须装不进去**） |
| `WIRE` | 线走得通吗（空腔连通域） |

### 机器**查不了**什么

诚实列出来，免得产生虚假的安全感：

* **桥接跨度** —— 没有自动检查，靠切片预览；
* **壁厚 / 悬垂** —— 是**采样**，不是证明；
* **配合手感**（多紧算紧、多松算松）—— 只能试打；
* **实际光照效果**（有没有残余高光）—— 只能上电拍照；
* **长期蠕变、疲劳**；
* **`watermeter-dn25.step` 的一切** —— 它是 DN25，尺寸不对，
  代码里被标成 `ILLUSTRATIVE`，任何判定都不许引用。

## ③ 人工审图

`python build.py build` 之后，人要看三样东西：

### 3.1 `out/assembly.step` —— 整体渲染

用 CAD / FreeCAD / 在线 STEP 查看器打开。重点看：

* 有没有"看起来就不对"的悬空、穿模、比例失调；
* 走线路径是不是真的通；
* 从 +Y 方向看过去，手能不能伸到该伸的地方。

> 这一步不能省。**本项目所有结构性错误都是人在渲染图上发现的。**

### 3.2 `out/sensor_view.svg` —— 模拟相机画面

这是"验证 ESP32-S3-CAM 能读到表盘"这件事唯一能给人看的东西：

* **绿点** = 该处表盘可见（光线追踪全程畅通）
* **红点** = 被挡住（`OPT-01` 也会同时报 FAIL）
* 绿圈 = 可视表盘 Ø56.5，蓝虚线 = 设计 ROI，橙框 = 字轮窗
* 右下角的橙色标尺 = 一个数字的成像宽度

**注意画面是左右镜像的**（光路含 1 次反射）。固件标 ROI 时按这个方向。

### 3.3 切片预览（Bambu Studio）

按 DESIGN.md §5.9 的推荐姿态摆好，看：

* 支撑生成量是不是符合 `DFAM-01` 报的悬垂占比；
* 有没有超过 15mm 的桥接；
* 薄壁处的走线圈数是不是够。

**人工审图发现的问题，先想"这能不能变成一条规则"。** 能就去补规则。

## ④ 试打验证

### 4.1 顺序：先小件，后整机

打一次整机 body 要几个小时、160g 料。所以按风险排序，**分批试**：

| 批次 | 打什么 | 验证什么 | 为什么排这个顺序 |
|---|---|---|---|
| **T1** | 只打抱箍那一段（Z −12~+8 切一片） | 内棱过盈量对不对 | 这是最贵的未验证假设，也是最便宜的试件 |
| **T2** | 镜片托板 + 两个托台的局部 | 托板坐不坐得平、提手好不好抓 | v2.3 实物就死在这里 |
| **T3** | 吊舱（Y 76~100 切一段） | 摄像头模组进不进方腔、板卡止不止得住 | 前腔尺寸这一版做了大改 |
| **T4** | 整机三件 | 装配顺序、走线、光路 | 前三项都过了再打 |

切局部试件的办法：在 `build.py` 里临时 `body & bx(...)` 导出即可，
不要为了试件去改主模型。

### 4.2 每次试打必须记录

在 `CHANGELOG.md` 里记一条，格式：

```
## T1-2 抱箍试件（2026-xx-xx）
- 打印：PETG，0.2 层高，5 圈
- 结果：套上银圈需用力，转不动 ✓ / 拧到底仍能转 ✗
- 实测：套入后内棱压痕深度约 ?mm
- 结论：collar_rib_interf 0.25 → ?
- **新增自检**：（如果这次发现了新的错误类别）
```

### 4.3 试打发现问题之后

**顺序不能反**：

1. **先问"机器为什么没拦住它"**；
2. 能变成判据的 → 去 `checks/` 加规则，跑一遍确认新规则**确实会报 FAIL**；
3. 然后才去改设计；
4. 再跑一遍，确认规则变绿。

> 第 2 步里"确认新规则确实会报 FAIL"很重要 —— 一条永远为真的检查
> 比没有检查更糟糕，因为它给人虚假的安全感。
> 本项目就出过这种：`POKA-01` 第一版写成"调头会干涉"，
> 而实际失败模式是"调头会悬空"，判据方向完全相反，那条检查永远为假。

## 提交前检查表

- [ ] `python build.py check` 阻断性失败 = 0
- [ ] 新增的结构有对应的新增自检项
- [ ] 新增的自检项**验证过它会在错误时报 FAIL**（故意改坏一个参数试一次）
- [ ] `out/report.md` 一起提交
- [ ] 动了参数 → `DESIGN.md` 的对应数字也改了
- [ ] 动了装配顺序 → `python build.py doc` 重新生成 `ASSEMBLY.md`
- [ ] 试打过 → `CHANGELOG.md` 记了一条

## 给 AI 协作者的额外说明

如果你是接手这个项目的 AI：

1. **你看不到渲染结果。** 不要假装能看见，那只会浪费双方一轮。
   需要人看的时候直接说"这一步需要你看一眼 `out/assembly.step`"。
2. **`build.py check` 是你唯一可靠的反馈来源。** 改完一定跑。
3. **报告里的 `why` 字段是给你看的。** 某条 FAIL 时先读它，
   判断这是"设计真错了"还是"规则本身该改"。两者都可能。
4. **不确定就标不确定。** `params.py` 有 `[估算]` 前缀，
   `checks` 有 `WARN` / `INFO` 级别，用它们，别把猜测写成结论。
5. **改动要可回滚。** 一次只改一件事，跑一次自检，再改下一件。
   一次改五处然后自检报了三个 FAIL，你分不清是谁导致的。
